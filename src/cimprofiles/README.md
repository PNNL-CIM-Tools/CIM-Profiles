# CIM Data Profiles

This package contains the Python data profile modules used by cim-graph
(and any other tool that wants the CIM classes without a database stack).
Each profile is a package of dataclasses generated from a CIM UML export
(via CIMTool or Enterprise Architect Schema Composer).

## How profiles are selected

In cim-graph, set `CIMG_CIM_PROFILE` to the dotted module path of the profile you want:

```bash
export CIMG_CIM_PROFILE="cimhub_2023"
# or fully-qualified:
export CIMG_CIM_PROFILE="cimprofiles.cim17.cimhub_2023"
```

Profiles live under their CIM version (`cimprofiles.cim17.cimhub_2023`). A short name,
optionally with a sub-profile (`cim18gmdm.connectivity`), is looked up in
`cimprofiles.PROFILE_PACKAGES` by `cimprofiles.profile_module`. The pre-0.6
`cimgraph.data_profile.<name>` paths still work and resolve the same way.

### Multi-profile merge — new in 0.5

Comma-separate two or more sub-profile paths to merge them at runtime:

```bash
export CIMG_CIM_PROFILE="cimprofiles.cim18.cim18gmdm.connectivity,\
cimprofiles.cim18.cim18gmdm.electrical,\
cimprofiles.cim18.cim18gmdm.asset"
```

`get_cim_profile()` calls `merge_profiles()` once and memoises the result.
Every caller in the same process — `XMLFile`, `FeederModel`, any utility
function — receives the **same module object**, so class identity is
maintained across all graph key lookups.

The merged module satisfies the same contract as any single profile: it has
an `__all__` list and each class is accessible via `getattr(merged, name)`.

### cim18gmdm — EPRI GMDM split profile

The GMDM model is split into sub-profiles by functional area. Use the
pre-baked merged package (`cim18gmdm`) for a single-import experience, or
compose the sub-profiles you need at runtime via the comma-spec.

#### Pre-baked merged package

```bash
export CIMG_CIM_PROFILE="cimprofiles.cim18.cim18gmdm"
```

This is a committed `cim18gmdm.py` and `__init__.py` generated by
`python -m cimprofiles.build_merged_profiles`. It defines the 116 classes of the five
sub-profiles merged, and is the equivalent of setting the comma-spec to all five sub-profiles.
Use it when you need every profile class available statically (e.g. for
Pylance completion on the full model).

#### Sub-profiles

## Loading split exports

For models spread across multiple part files, use an IEC 61970-552 metadata
header (`.cimx` file) to load all parts in one call:

```python
import os
from cimgraph.databases import XMLFile
from cimgraph.models import FeederModel

os.environ['CIMG_CIM_PROFILE'] = (
    'cimprofiles.cim18.cim18gmdm.connectivity,'
    'cimprofiles.cim18.cim18gmdm.electrical,'
    'cimprofiles.cim18.cim18gmdm.asset'
)

# 9500node.cimx lists the individual part files as dcat:Distribution entries.
# XMLFile resolves each accessURL relative to the .cimx file and loads all
# parts into one graph in a single two-pass read.
file    = XMLFile(metadata='profile_parts/9500node.cimx')
network = FeederModel(container=None, connection=file)
```

The `.cimx` format follows IEC 61970-552 §8. Each part file is a
`dcat:Distribution` with an `accessURL` (relative path) and a
`dcterms:conformsTo` URI naming the sub-profile it was written against.

## Adding a custom profile

1. Export your UML profile from CIMTool or Schema Composer as `.xsd`.
2. Run `uv run xsdata generate` (or the equivalent CIMTool builder) to
   produce the dataclass package.
3. Place the generated package under `src/cimprofiles/` (or any importable package).
4. Set `CIMG_CIM_PROFILE` to the dotted path of the package.

For split profiles, generate one sub-package per functional area and use
the comma-spec to merge them at runtime.

## Generating a pre-baked merged package for a split profile

A pre-baked package lets users `import cimprofiles.<version>.<name> as cim`
without knowing the sub-profile names, and lets Pylance/mypy resolve the full
merged class surface statically.

### 1. Import the parts

Import each CIMTool profile as a sub-package of the merged package (the module is named
after the last path segment), then remove duplicate fields:

```bash
scripts/import_cimtool_output.sh cim18 cim18v15/Profiles/substation.cimantic-graphs.py \
    cim18v15/Profiles/substation.__init__.py cim18v17/substation
uv run python -m cimprofiles.dedupe_profile_fields
```

The merged package needs an `__init__.py` (an empty one will do) before the first build.

### 2. Register the release in `merge_releases.yaml`

```yaml
releases:
  - name: my_profile          # the merged module is <package>/my_profile.py
    package: cimprofiles.cim18.my_profile
    parts:                    # the generated modules, not their packages
      - cimprofiles.cim18.my_profile.connectivity.connectivity
      - cimprofiles.cim18.my_profile.electrical.electrical
    description: "My profile — merged from connectivity + electrical"
```

`parts` is ordered; where parts differ, the earlier part wins.

### 3. Run the build script

```bash
uv run python -m cimprofiles.build_merged_profiles
```

For each release this writes, and smoke-tests the import of:

- `<name>.py`: every class of every part, merged at the source level. Fields, enum
  members, properties and docstrings are copied verbatim from the CIMTool output, so the
  file reads like any other generated profile, with hover docs in Pylance.
- `__init__.py`: re-exports the merged classes.

Classes that appear in several parts are merged by name:

- **Base class:** CIMTool drops intermediate classes a profile does not use, so one part
  may declare `Terminal(Identity)` and another `Terminal(ACDCTerminal)`. The most
  specific candidate wins (`cimprofiles.merge.most_specific_base`). Unrelated candidates
  raise.
- **Fields and enum members:** the union. A field defined by several parts keeps the
  serialized association end, else the earliest part's. A different type or inverse is
  logged as a UML conflict.
- **Stereotypes:** the union. **Docstrings, properties and CIMUnit classes:** the first
  part's. A property or enum value that differs between parts raises.

`tests/test_build_merged_profiles.py` fails if a committed package is out of date with its
parts, so re-run the build after regenerating any part.

## Runtime merge internals

`cimprofiles.merge.merge_profiles(*modules)` builds a synthetic
`types.ModuleType` by:

1. Collecting every name from each module's `__all__`.
2. Topologically sorting by inheritance (parents before children).
3. For classes that appear in more than one sub-profile: creating a new
   dataclass with the **union of direct fields**, reparented onto the
   already-merged base class.
4. For classes that appear in only one sub-profile: adopting the class
   as-is but reparenting it onto the merged base if the base was rebuilt.
5. Enums, CIMUnit subclasses, and the shared `Identity` root are taken from
   the first profile that defines them.

When sub-profiles declare different base classes for the same class name, the most
specific one is used (`most_specific_base`); unrelated bases raise rather than silently
drop a lineage.

To generate a static type-stub file for Pylance/mypy (the replacement for
the hand-maintained `canonical.py`):

```python
from cimprofiles.cim18.cim18gmdm import connectivity, electrical
from cimprofiles.merge import generate_type_stubs

generate_type_stubs(connectivity, electrical, output_path='cim_merged.pyi')
```
